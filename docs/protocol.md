### 1.1 后续训练统一工作集 v2

用户批准扩大验证范围并均衡 worker 覆盖，原因是 dev5 不足以判断拟合与泛化。工作集成员另存 [workset_v2.json](../protocol/workset_v2.json)，**原 split_v1.json 的成员、顺序和字节保持不变**；工作集只在各自原集合内选样，不迁移分片、不重切完整数据池。

| 工作集 | 布局数 | 固定选择规格 | 用途 |
|---|---:|---|---|
| train | 20,000 | 100 个 worker 各 2 个 train 分片，每片 100 例 | 训练 |
| dev | 2,500 | 100 个 worker 各 5 个 dev 分片，每片 5 例 | 阶段评估与模型选择 |
| local_test | 2,500 | 100 个 worker 各 5 个 local_test 分片，每片 5 例 | 默认封存；本次冻结方案的单次测试授权见 1.3 |
| train_monitor | 500 | 嵌套于 train，每 worker 5 例 | 固定训练误差与拟合诊断 |
| dev_monitor | 500 | 嵌套于 dev，每个入选分片 1 例 | 训练中的定期验证、学习率下降与早停 |
| dev_quality | 100 | 嵌套于 dev，每 worker 1 例 | 固定 checkpoint 的合法化质量对照 |

工作集索引记录选择算法、种子、原划分哈希和成员。选择只依赖冻结路径与行号，不能根据模型成绩挑选成员；生成和校验 local_test 索引时不读取其张量或标签，实际读取须有独立的冻结测试授权。worker 均衡不等于模块数精确分层；train/dev 输入的规模、约束分布需另行诊断并报告，不能假定测试分布已核验。

正式训练默认采用完整 20,000 例 train、固定 500 例 dev_monitor，结束后对所选最佳 checkpoint 在完整 2,500 例 dev 统一评估预测误差；合法化后的 Q 使用固定 dev_quality 100 例，明确记录耗时预算。若训练时间上限使终末评估未完成，结果明确标为评估待完成，并保留最佳 checkpoint 供单独评价，不把不完整面板当成完整 dev 结论。5 例限制适用于日常代码功能检查，不替代用户批准的上述正式研究评估。超出该工作集的训练或评价必须先写明新方案，不能自动扩读未选数据。

### 1.2 训练与拟合判断的基本要求

- 训练与验证模式明确分开；固定面板用 eval 模式、不反向传播，分别记录中心位置误差、形状误差和总监督损失。不同 mini-batch 的即时 loss 不直接用于判断收敛。
- 默认采用验证停滞时降低学习率（如 ReduceLROnPlateau）与早停；实验开始前固定验证频率、主监测指标、相对/绝对 min_delta、学习率下降倍率及 patience、最低学习率、早停 patience。早停应给降学习率后的训练留出观察机会。具体数值以实验说明和运行 config 为准，不按查看测试成绩调整。
- 分别保存验证表现最好的 best 和可恢复的 latest checkpoint，记录 optimizer、scheduler、早停计数、训练位置、随机数状态和累计预算。恢复必须沿用同一工作集与预算账本；从头重训使用新目录，不能覆盖旧权重或混为续训。
- 训练日志保留固定 train_monitor 与 dev_monitor 曲线，并注明 train_monitor 中实际见过/未见过的样本数；必要时分开对比，避免把未训练到的样本误称为训练拟合证据。完整 dev 结果用于核对监测面板是否具有代表性。
- 监督误差与最终布局质量分开报告；降低位置/形状误差并不保证合法化后的 Q 改善。欠拟合、过拟合、优化困难与目标不对齐的判断必须有固定面板证据。
- 时间/步数上限是资源保护，不是收敛判据；验证早停也只说明在当前指标与 patience 下停止改善，不能保证全局收敛。

## 2. 策略阶段先发散，再调优

先建立可运行且满足硬约束的简单参照，目的是让比较有意义，不把它发展成无休止的局部优化工程。

早期每轮保留 3–5 个机制明显不同的假设，允许推翻表示、目标函数、搜索流程、模型结构或学习范式。例如约束规划/MILP、可微坐标优化与合法化、拓扑搜索、约束优先构造、学习引导搜索、生成模型，以及这些方法的混合。候选按预期机制、可行性、算力和适用场景筛选，不要求把所有路线都实现。

- 不默认在现有网络上加层、调学习率或反复改 SA 温度；新路线可以完全重置架构。
- 早期只调整使策略正常工作的必要参数，先用小预算检验方向；没有机制证据就不扩大训练量。
- 每条路线写清：为什么可能有效、什么观察会推翻它、停止投入的条件。失败结果记录结论后淘汰，避免换名字重复尝试。
- 后期选定表示、架构与求解流程后，才系统调优超参、工程性能和资源分配。

## 3. 必须解释改善来自哪里

实验前用几句话固定假设、主指标、对照、预算和种子；实现后记录实际变化与结果，不倒推“假设”。

策略探索允许一次改变多个部分，但胜出后必须做最少的关键归因：移除新增机制、恢复旧模块，或做能区分两种解释的反例。不能仅凭一个总分下降就归因为“新架构有效”。要区分：约束处理、表示能力、搜索行为、训练数据、更多算力、实现加速或随机性。

比较固定数据、种子和资源口径。默认初筛 seed=0；只有足以影响策略取舍的结果才扩大到固定 3 个种子，不为每个小改动重复全套实验。保持输入信息一致，不以标签泄漏、关闭硬约束或多用算力换取虚假改善。

报告至少包括：硬约束通过率、HPWL gap、bbox 面积 gap、三类软违反、耗时及资源预算。不可行样本仍计入主指标；仅在可行样本上统计的质量必须另行标注，不能用它掩盖失败率。本地质量分、实际运行时间和正式含跨提交中位时间的分数分开说明。

## 5. 测试保持轻量

- 默认只做改动相关的语法/导入、一个批次或最多 5 例功能检查，以及所改变约束/行为的直接验证。
- 优先复用现有校验器、已保存输出和失败实例，不为每个脚本搭完整测试框架，不写逐行复制实现的测试。
- 数据/版本不变就不重复下载、解压或全量哈希；官方来源核验是阶段性检查，不是每次改动的测试门槛。
- 新约束处理必须包含一个实际违反案例或一个针对性反例；计分/数据接口改变时再加必要回归，不默认跑 100 例。
- 检查通过后转向研究结论；没有新失败或新风险时不反复扩测。测试规模与宣称的证据强度匹配。

## 6. 工程和记录尽量少

文件归属遵守 [结构管理规范](workspace_structure.md)。使用独立 conda 环境，不修改 base；官方原件放 third_party/references，自研内容按实验独立维护。

每个实验的代码、设计、专用入口和结论在 experiments/<实验名>/，每次运行在其 runs/<run_id>/。通常只需实际 config、results 和必要日志；不重复保存坐标与多份同义报告。项目状态归根 README，实验状态归实验索引，详细解释归所属实验，AGENTS 不记进度。

复用 datasets 的数据处理、scoring 的官方输出评分及 visualization 的纯展示绘图（2026-10-17用户指定统一样式）。训练 Loss、代理目标、模型、构造、搜索、合法化等由实验独立维护，允许复制，不跨实验导入私有代码。绘图模块仅消费坐标/约束/已存指标，不读取数据或运行算法。评分模块直接使用未修改的官方规则；本地中性时间质量对照与正式比赛分数分开报告。

入口记录解析后的数据路径、命令、版本、种子与预算；物理位置由 protocol/paths.json 解析，冻结 split_v1.json 不因迁移改写。历史运行 JSON、日志和 checkpoint 中的路径、命令与哈希保持原始事实。

源码采用本地 Git 的可追溯提交并连接 GitHub origin；必要时补充小型源码快照，不以哈希冒充可恢复源码。数据、环境、缓存和完整 checkpoint 不提交 Git。只在依赖或接口改变时修订核心文档。

## 7. 整理旧版本

每轮策略筛选结束和阶段交接时整理，不自动创建定时任务。有效参照仍在使用时留在原实验；淘汰路线先记录原因，再将必要代码版本、说明与证据一起归档到 history，确认可读后移除散落副本。

结构迁移集中保存旧新路径、必要完整性证据及小型迁移前源码快照；旧归档保留原件，恢复时结合映射。不要为统一新路径批量改写原始运行记录或冻结协议。

重复结果、空日志、完成安装后的缓存与过期下载分片可在核实后清理，不把垃圾全塞进历史。清理前检查运行状态与引用，保护活跃输出、原始资料、数据、有效环境和唯一 checkpoint；不明用途先核实，删除唯一复现证据须由用户明确决定。

## 8. 补充约定

先解决合法性和测量正确性，再比较优化质量；始终保留一个可独立复核的硬约束检查。不要为了让数字好看而修改评分定义。

把算法质量、执行效率与设备利用率分别测量；安装 CUDA 不等于 GPU 加速，换硬件、线程数或预算都要说明。一次跑完不等于收敛，一次胜出不等于机制已被证实。

出现基线异常时先检查协议、输入、标签和实现支持范围，先完成最小反例，避免直接消耗一整轮长任务。

用户明确要求删除已废弃方向时，以该请求为准；清理应覆盖代码、权重、结果、设计和旧源码归档中的相关内容，避免后续实验误用。保留通用规则、官方原件、数据与用户指定的基线证据。
