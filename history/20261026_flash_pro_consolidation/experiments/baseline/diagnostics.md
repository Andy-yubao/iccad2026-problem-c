# 官方模板问题核查：5 例对照

> 当前诊断入口与证据已并入本基线目录；历史真实命令、哈希和路径以 runs 内原始记录为准。


## 结论

后续已完成更详细的[官网入口、分支、版本历史及数据版本复核](version_check.md)：没有发现下载错误或新旧文件混用，5 例数据还与官方 GitHub 所带文件逐个匹配。

**选中 5 例的直接失败原因是官方模板未实现当前比赛要求的 fixed-shape / preplaced 硬约束处理。没有发现这些样本的数据字段错位、输入/标签配错或评测器误判合法解。**

“100 例正常执行、0 例可行”不能作为算法已有效复现的结论。这次核查只覆盖 5 个实例，不声称其余 95 例不存在其他问题。后续验证默认限定 5 例。

原版模板是可运行的算法起点，官方文件自身注明不处理 fixed、preplaced、MIB、cluster、boundary；不能直接将它作为满足当前完整规则的合法基线。此前应先做这类约束检查，再决定是否运行全部 100 例。

## 核查范围和方法

选定公开验证索引 **0、19、39、69、99**，对应 **21、40、60、90、120** 个模块。

- 复用已完成 100 例中的这 5 个布局，没有重跑耗时的 SA，也没有重新评测其余 95 例。
- 在新的独立 conda 环境 `.conda/envs/iccad2026` 中，对每例进行三组检查：保存的原版输出、数据自带参考布局、仅使用求解器合法输入构造的可行性对照布局。
- 三组布局均用原版 `evaluate_solution()` 评测，并以独立 Python 几何/面积/规格检查交叉验证硬约束。使用 runtime=median=1，仅核查本地中性 runtime 分数，不重测性能。
- 独立从原始多边形标签提取 `(x,y,w,h)`，与评测器得到的 target 完全一致；用独立 NumPy 实现复核 b2b/p2b HPWL 和 pin/block 索引顺序。
- 对这 5 例的 10 个数据文件核对安装时记录的官方归档内容 SHA-256；对模板、评测器、验证加载器核对归档哈希。
- 实时检查 GitHub main：仍是 `aadddcc2238695eb21e6542b8a6cd9e9fe6b80fa`，这三个文件均与工作区完全一致。不是本地误改或漏取了已经发布的新版本。见[在线核对记录](runs/template_version_check/content_hashes.json)。

这 5 个原版输出的 cost 都为 10。参考布局的 cost 为 1.090849、1.133148、1.000000、1.079959、1.126824；它们都硬约束合法，部分仍有软约束违反。参考布局不是必然达到零软违反、cost=1 的答案。

仅输入对照保留所有 preplaced 块，其他块按合法尺寸放在其右侧的一行中。它只读取普通块的面积、fixed 块的宽高、preplaced 块的合法位置与尺寸；**不读取自由块的参考位置、参考形状或参考 metrics**。所有 5 例硬约束都通过，证明不需要完整参考答案，也能构造出合法解。

对照布局非常差，HPWL 和面积代价很高，5 例 cost 都触及可行上限 9.999999。它仅是可行性证据，不能称为有竞争力的修复算法，也不能把这个接近 10 的分数当作质量改善。

## 根因一：无条件旋转固定块

在 [optimizer_template.py](../../third_party/FloorSet/iccad2026contest/optimizer_template.py) 中，`solve()` 初始化时会从 `target_positions[:,2:4]` 读取 fixed/preplaced 的尺寸，但 SA 后续执行：

```python
tree.move_rotate(random.randint(0, block_count - 1))
```

它没有排除 fixed 或 preplaced。`move_rotate()` 直接交换宽高；当前比赛的固定形状要求 `(w,h)` 精确匹配输入，不允许把非正方形宽高互换。

可复核实例：21 模块用例的块 15 为 fixed-shape，规格宽高 `(18,26)`，原版输出 `(26,18)`。这不是浮点容差造成的小偏差。

## 根因二：预放置位置没有被锁定

模板只使用 `target_positions` 的宽高列，未使用 preplaced 的 `(x,y)` 来约束布局。B*-tree 从自己的根和 skyline 重新安排所有块，预放置块也随之移动。

同一 21 模块用例的块 17 要求 `(x,y,w,h)=(71,0,18,26)`，原版给出约 `(33.906,61.267,26,18)`，位置和尺寸都改变。120 模块实例中还有尺寸保持不变、但位置改变的 preplaced 块，因此只禁止旋转不能解决全部问题。

每例原输出、规格、违反块编号均保存在审计 JSON 中。

## 根因三：搜索代价不检查这些约束

模板 `_cost()` 为：

```python
return hpwl_b2b + hpwl_p2b + area * 0.01
```

它既不以硬约束过滤候选，也不对 fixed/preplaced 规格违反加罚；grouping、boundary、MIB 也没有进入搜索代价。这样即使某次随机操作生成非法解，搜索仍可能将其视作最优解保存。

官方 README 的更新记录说明 fixed/preplaced 已改为硬约束；评测器按这套规则判定。模板的约束支持没有同步补齐。因此这里是**模板实现与完整比赛规则不匹配**，并非已发现的数据存储格式与加载器不匹配。

## 排除的数据和评测疑点

- 加载器的 `config_21`–`config_120`、输入文件和标签文件配对正确，选中样本的块数量正确。
- 验证标签是多边形，评测器正确提取 `(x,y,w,h)`；没有将训练标签的 `(w,h,x,y)` 顺序误用于这批验证数据。
- 仅 fixed 块尺寸、preplaced 块位置与尺寸被传入 `solve()`；普通块的 target 位置仍为 `-1`。这一接口与模板声明一致。
- 参考布局均无硬约束违反，参考 HPWL 与存储 baseline 的相对差异约在 `3.1e-8` 以内，属于浮点精度量级；bbox 面积一致。
- 独立硬约束检查与原版评测器对三类布局的可行性、规格违反块数完全一致。
- GPU 是否参与不是这些非法几何结果的原因。该 SA 在 CPU 上运行，已保存布局中的真实尺寸和位置违反足以解释这 5 例的不可行判定。

以上是对所选 5 例和相关逻辑的排查，不是评测器全部功能均无缺陷的证明。
