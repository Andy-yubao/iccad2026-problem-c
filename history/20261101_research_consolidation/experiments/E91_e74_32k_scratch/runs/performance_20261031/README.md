# E91吞吐诊断与逐位等价加速原型

2026-10-31，用户观察GPU利用率约60%，要求排查和寻找加速方法。实际训练保持原代码，不改模型、32k成员、顺序、batch32、FP32、Loss、Adam、步长规则或预算。本轮已接近2h预算结束，停止后重新读取/附加32k端口数据约需数分钟，故不在末尾迁移生产入口。

## 真实训练日志

用同一轮内相邻100步的时间差，避开每轮监测和启动读数据，保留周期存盘开销：

| 实验 | 每步中位耗时 | 最近30个区间中位耗时 |
|---|---:|---:|
| E91：本轮32k从头训练，新Loss | 200.32ms | 201.71ms |
| E90：E74权重16k后训练，同一新Loss | 199.56ms | 199.87ms |
| E74：32k旧Loss、图聚合冻结 | 161.75ms | 161.08ms |

E91与同新Loss的E90单步速度相近，较旧E74约慢24%。每轮E91有1000步而E90只有500步，不能用轮耗时比较。GPU利用率是采样窗口内的忙碌时间，不能单凭90%→60%推断吞吐下降三分之一。历史电源、负载及目标定义不同，本表不是严格同硬件负载消融。[历史日志统计](historical_step_timings.json)。

## 开销来源

当前CUDA图只包含前向、固定Loss、反向和梯度裁剪。AdamW与0.5%联合参数位移保护仍在图外，`GraphStepControl`对每个Linear/LayerNorm组由Python逐个提交复制、平方、求和、缩放和回写，产生大量细小CUDA调用和调度间隙。每步另外有有限值检查导致的两次GPU/CPU同步。

显存修复后每步主机装配再拷贝batch，也会留出CPU等待；但五例热缓存片段测量：CPU装配加CPU复制约8.75ms，装配加H2D约9.47ms（固定32输入14.64MiB）。二者差约0.7ms，只能作量级判断，不能把共享GPU下的相减当作精确PCIe耗时；该结果不支持H2D带宽是主要瓶颈。

同一隔离副本上，原步长保护片段约168.59ms，捕获成图后约5.72ms。该片段明显值得优先优化，但与整步计时的条件不同，不能直接相加或称其精确占比84%。[片段结果](results.json)、[脚本](benchmark.py)。

旧Loss与新Loss的算子不同，新Loss包含GPU Prim分组树；E91还训练原来被冻结的24个图聚合参数张量。因此对旧E74的速度差不能全部归到新数据搬运，更不能仅凭利用率诊断算力或硬件故障。

## 已验证的加速方案

[CapturedProjection原型](projection_prototype.py)将原`before/after`中的相同算子分别录入CUDA图。Adam仍在图外运行，实时LR和0.5%保护规则不变，没有替换求和顺序、融合数学公式、AMP或改变目标。捕获时不改变参数和统计计数，重放时按真实步数更新计数。

原型先通过有/无裁剪的多种合成提议，参数、scales、clipping计数逐位一致。随后使用同五个真实训练成员（1683/10027/5474/18140/25001）、真实checkpoint的Adam矩、相同Dropout随机状态，分别执行10个隔离训练步：

| 路径 | 单步中位耗时 |
|---|---:|
| 现有图外逐组保护 | 331.17ms |
| 捕获保护算子 | 141.01ms |

隔离微基准比值2.35倍。10步Loss序列、全部模型张量、Adam状态、CUDA RNG、scales和裁剪计数逐位一致，FP32、batch32、Dropout和Loss不变。[整步结果](whole_step_results.json)、[脚本](whole_step_check.py)。

**限制：**测试与正式训练共享GPU，且重复同五例的热batch；整步计时不包含真实32k装配、监测、读盘和存盘。不能承诺正式整轮2.35倍，更不能拿331ms与历史200ms相减估计收益。两份计时的环境和负载不同。
