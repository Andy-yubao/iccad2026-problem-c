# E91显存问题修复与新2小时预算

2026-10-31，用户查询状态时核实：旧进程启动约一小时后仍停留epoch0/step0，初始dev500尚未完成。全部32k输入的GPU常驻张量为14.502GiB；Windows进程计数器记录独立显存16,668,323,840字节、共享显存2,495,610,880字节、总提交19,163,934,720字节，支持显存超额提交和严重换页。不能把这段时间称作完成训练，也没有训练质量结论。

先写E91全局STOP请求安全暂停；其未及时响应后，仅结束已经核实命令和PID的训练子进程34452，原控制器47564随后退出。epoch0原始断点保留。按UTC调用起止保守计入3870.768777秒，替代卡住前的647秒旧心跳；模型、Adam、随机状态和进度没有清零。

修复只改变数据驻留和搬运：32k缓存行保留在CPU，按原顺序将每个batch32填入小型固定页锁定缓冲，再复制到CUDA图的固定输入。主机写缓冲前等待此前异步拷贝完成，避免复用时覆写在途数据。没有减少数据、端口、batch、精度、Loss或padding尺度，也没有给模型添加新算法。

五例检查逐张量验证新旧批次、重排/重复成员及out复用完全一致；虚拟32k（复用这五例）验证构造器不按数据量分配GPU数组。相同Loss/梯度/一步更新、全12层更新幅度边界、真实Dropout/Adam恢复逐位一致及非有限值保护均通过。最后检查只用原五个真实训练成员，没有新增大规模推理或Q。

用户随后明确要求“修复好问题后请你自行在后台重启训练，记得把预算恢复2h”。因此保留旧费用3870.768777秒，新增7200秒可用训练窗口，总阶段上限变为11070.768777秒；原18小时累计上限继续执行。恢复时的载入和监测仍计入新窗口。没有把旧运行或费用改写为不存在。

迁移只改checkpoint的源码/驻留方式身份、对应登记哈希、授权预算和暂停状态；逐项核对模型、Adam、调度、Python/NumPy/torch/CUDA随机状态、采样次序/游标/seen以及图步长计数全部不变。第一次绑定后的通用校验器未处理NumPy数组，最终迁移已对中间绑定作显式审计，并在写入前后使用支持NumPy的精确校验；所有原证据保留。

已从原checkpoint后台恢复，控制器49892，命令`python -u -B -m experiments.E91_e74_32k_scratch.pipeline --resume`。本入口只训练，测试仍封存。

恢复观察：正式32k初始dev500监测已完成，Loss16.297576；训练已记录至少200步，检查保存的模型张量和Adam状态证实实际发生参数更新，全部12层图聚合权重均与起点不同。实际显存约3392MiB，单batch32输入14.64MiB，不再以全池14.502GiB常驻。瞬时batch Loss不与固定开发Loss混作收敛证据，首轮固定监测尚待完成。[恢复观察证据](recovery_observation.json)。
